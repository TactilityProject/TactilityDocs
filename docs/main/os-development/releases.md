# Releases

Tactility releases consist of firmware for every supported device, TactilitySDKs for app development, and a simulator build. GitHub Actions builds and publishes them.

## Versions

The current version is in `version.txt` (e.g. `0.8.0-dev`). It ends up in:
- the firmware, shown in System Info
- the SDK's folder name (`<version>-<platform>`), which apps refer to with `target.sdk` in their manifest

## Automated builds

The "Build Firmware" workflow (`.github/workflows/build.yml`) runs for pull requests, pushes to `main` and version tags:

1. **SDKs:** builds a TactilitySDK for every ESP32 target (from the `generic-esp32*` devices) and for the simulator (POSIX).
2. **Firmware:** builds the firmware for every device in `Devices/` (the list is generated by `Buildscripts/gh-generate-device-matrix.py`).
3. **Bundle:** bundles the build artifacts.
4. **Publish:** uploads the firmware and SDKs to the CDN (`https://cdn.tactilityproject.org`):
   - a push to `main` publishes a **snapshot** firmware (the Beta channel), and the SDKs when `version.txt` ends with `-dev`
   - a tag that starts with `v` (e.g. `v0.8.0`) publishes a **stable** firmware (the Main channel), and the SDKs when `version.txt` doesn't end with `-dev`
   - a commit of a pull request publishes a **develop** firmware after a reviewer approves it (see [Develop builds](#develop-builds))
   - a push to `main` also publishes the [tt tool](../app-development/tt.md) (`sdk/tt.zip` and `sdk/tt.json`)

So a release's SDKs come only from its tag, and later pushes to `main` can't overwrite them.

Every SDK version on the CDN (`sdk/<version>/`) has the SDK of each platform, and `tools.zip` (the tools that `tt` runs for that version, with the project templates of `tt app create` in `NewProject/`: a `gui`, a `terminal` and a `module` variant). `index.json` lists them all. The CDN feeds the [Web Installer](../user-guide/installing-firmware.md), and `tt` downloads the SDKs and tools from it.

"Build Simulator" builds the simulator for Linux and macOS, and "Tests" runs the unit tests.

## Release channels

| Channel | Shown as | Built from | CDN folder |
|---|---|---|---|
| `stable` | Main | tags `v*` | `firmware/stable/` |
| `unstable` | Beta | pushes to `main` | `firmware/snapshot/` |
| `develop` | Develop | pull requests, and local builds | `firmware/develop/` |

A build stores its channel, its git commit and its build time, which `Buildscripts/generate-build-info.py` writes to `build/build_info.json` and into the firmware (`Tactility/Private/Tactility/BuildInfo.h`). The channel comes from the `TT_BUILD_CHANNEL` environment variable (`stable`, `unstable` or `develop`), which the CI sets per build. Without it, a build is `develop`. The build time stays the same while the commit doesn't change, so incremental builds don't recompile. System Info shows the commit as "Build" and the build time as "Created".

The channel of the firmware is the default update channel of the device (see [Software Updates](../user-guide/software-updates.md)).

## Firmware updates

For every device, `Buildscripts/CDN/generate-firmware-files.py` writes these files to the channel's folder:

| File | Used by |
|---|---|
| `<device>.json` | The [Web Installer](../user-guide/installing-firmware.md): the parts to flash and their offsets |
| `<device>-ota.json` | The update service of the device |
| `<device>-<build id>-Tactility.bin` | Both: the app image of the build |
| `<device>-bootloader.bin`, `<device>-partition-table.bin`, `<device>-ota_data_initial.bin` | The Web Installer |
| `index.json` | The Web Installer's device list |

The OTA manifest (`<device>-ota.json`):

```json
{
  "version": "0.8.0-dev",
  "gitCommit": "94d2316b52d38e4da89622ab1f25575ec36e1513",
  "created": 1795787182,
  "file": "m5stack-tab5-94d2316b52d3-Tactility.bin",
  "size": 5715280,
  "layoutId": "f82fd7a5b6925912429c8d9ea43d3bd5"
}
```

- `created` is the build time, in seconds since 1970. Within its own channel, a device installs a build when its commit differs from the running firmware and its build time is later. On another channel, any build with another commit is an update.
- `file` is the app image. The build id in its name (the first 12 characters of the commit) gives every build its own file, so a device that read a manifest just before a new publish still downloads the image that the manifest describes.
- `layoutId` is the MD5 that the partition table stores of itself. A device only installs an update with the same partition table, and an image that fits its app partition. Otherwise the update needs the Web Installer.

`Buildscripts/CDN/upload-firmware-files.py` uploads the images first and the JSON files last. JSON files get `Cache-Control: public, max-age=60`. After the upload, it deletes the app images of older builds: it keeps the 2 newest builds per device (`--keep-builds N`, or `--no-cleanup` to keep them all). `Buildscripts/CDN/purge-firmware-cache.py` then purges the Cloudflare cache of the uploaded files. It reads the `CLOUDFLARE_ZONE_ID` and `CLOUDFLARE_PURGE_CACHE_TOKEN` secrets (an API token with the Zone > Cache Purge permission). Without them, or when the purge fails, it only prints a warning.

An OTA update only writes the app partition: the bootloader and the partition table stay as they are. Don't rename or remove partitions, and don't change `CONFIG_PARTITION_TABLE_OFFSET`, without telling users that they have to install with the Web Installer.

### Develop builds

The `PublishFirmwareDevelop` job uses the `cdn-develop` GitHub environment. Give it **Required reviewers** in the repository settings: the job then waits until a reviewer approves it on the run's page. It isn't a required check, so a pull request can be merged while it waits. Pull requests from forks don't get the CDN secrets and don't publish.

### Testing updates

To test the update of a device with a firmware that is newer than the CDN build (for example one that you built yourself), tap the status label of the update card in the Software app 5 times within 3 seconds. The button then offers a forced update, which installs the build of the channel even when it isn't newer.

## Making a release

1. Set the version in `version.txt` (e.g. `0.8.0`).
2. Commit it, and tag the commit with the same version prefixed with `v` (e.g. `v0.8.0`).
3. Push the commit and the tag. The workflow builds and publishes the stable release.
4. Set `version.txt` to the next development version (e.g. `0.9.0-dev`).

## Device metadata

`Buildscripts/CDN/generate-firmware-files.py` creates the CDN's metadata for each device from its [device properties](../device-development/device-properties.md): `general.vendor`, `general.name`, `general.incubating`, `cdn.warningMessage` and `cdn.infoMessage`. Incubating devices and messages are shown in the Web Installer.

## Local builds

The `Buildscripts/` folder has scripts to package local builds:

| Script | Purpose |
|---|---|
| `release.sh <device-id>` | Copies the current firmware build (`build/`) into `release/Tactility-<device-id>`, with the flash scripts, and the `.elf` files with debug symbols into `release/Tactility-<device-id>-symbols` |
| `release-current.py` | Builds the TactilitySDK for the current build and exports the tools, into `release/sdk/<version>/` (see [Building TactilitySDK locally](../app-development/symbols.md#building-tactilitysdk-locally)) |
| `release-sdk-current.py` | Only builds the TactilitySDK for the current build |
| `release-tools-current.py` | Only exports the tools that `tt` runs, with `NewProject/`, into `release/sdk/<version>/tools` |
| `release-tt.py` | Creates `tt.zip` and `tt.json` for the CDN in `release/tt/` |
| `release-simulator.sh <build-dir> <target>` | Packages a simulator build with its `Data/` folders |

A firmware release contains `flash.sh` and `flash.ps1` to flash it with esptool, and `merge.sh`/`merge.ps1` to merge the binaries into a single image (see [Installing Firmware](../user-guide/installing-firmware.md)).

Keep the `-symbols` folder of every release you distribute: it's needed to decode crash backtraces from that firmware.
